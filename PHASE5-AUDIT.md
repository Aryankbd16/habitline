# Habitline Android APK milestone

## Stage A findings

The source baseline is `8dc549d88534089f81d97706e6e7bdc5907408fb` on `habitline_checkpointBranch`. The initial working tree was clean. The local `min` branch pointed to the same commit and `main` pointed to `b0cba97`. The root contains an independent historical copy in `baseline-checkpoint/`. The active product uses the top-level web, server and Android directories.

| Area inspected | Existing behavior and consequence for Android |
| --- | --- |
| Kotlin app and widget | Both read and rewrite `habitline_store/habitline_store_json`. The app creates and permanently deletes habits. A widget is bound to one UUID. A tap toggles today's state and updates its own instance. Separate reads and writes can lose concurrent edits. The JSON reader maps parse errors to an empty store. Migration must read the original bytes, validate before writing, retain widget IDs locally, and offer recovery on malformed input. |
| Dashboard, habits and history | The Express API owns the web data. SQLite stores fractional points, priority, icons, optional reminder time, local start, archive flag and prior schedule versions. The prototype stores integer points, creation time, weekday fields and date-only completions. Its calendar-day streak ignores weekdays. Related, Paired and Supports are associations. Completion remains independent. Difficulty requires an explicit additive model because the web habit schema has no difficulty field. |
| Analytics and goals | The web calculation modules and Phase 3 tests define Monday-start weeks, equal elapsed period comparisons, historical schedules, archived history, zero-opportunity results, saved points and insight thresholds. A goal counts unique linked completions in an inclusive window capped by today, target date and archive date. Preserve those results in shared dated fixtures. |
| XP, awards and challenges | Server transactions pair completion writes with append-only awards or reversals. Re-mark uses the first XP amount for that habit/day. Historical imports earn no retroactive XP. The signed ledger determines level with the configured level step. Milestones retain their earned snapshots. Challenge eligibility, dates, links and participation live in the Phase 4 server modules. |
| Social and preferences | The server authorizes friend requests, blocks, memberships, invitations, shared challenges, privacy-filtered rankings, published awards and reactions. Android needs owner-scoped, time-stamped cache entries, cache invalidation on revocation and visible connectivity state. Dashboard sections, categories and priority order come from profile personalization. Launcher bindings, OS permissions, notification delivery and device appearance belong on each device. |
| Existing backup and API | Web JSON v2 exports profile, habits, completions and relationships, with an empty settings array. Its import passes only the three tracking collections. It cannot transfer the complete ledger, goals, challenges, pairing state or deletion history. Preserve this legacy import separately from the new portable package. Existing session cookies and password hashes are authentication data and stay out of portable exports. |
| Storage and build | The live SQLite database has WAL sidecars. Use the online backup API for its recovery copy. The original Android module has a Gradle 8.7 properties file and lacks the wrapper binaries/scripts, Android tests and APK. Local JDK 17 is installed. Hosted SDK 34 and Build Tools 34.0.0 match AGP 8.5.2. |

The rule references are the [shared data model](shared/documentation/data-model.md), [Stage 2 audit](STAGE2-AUDIT.md), [Stage 2 changes](STAGE2-CHANGES.md), [Phase 3 report](PHASE3-REPORT.md), [Phase 4 audit](PHASE4-AUDIT.md) and [Phase 4 report](PHASE4-REPORT.md). The server schema and current calculation modules take precedence over older prototype documentation.

## Implementation choice

| Candidate | Fit for this checkout |
| --- | --- |
| Kotlin, Room and Jetpack | Reuses the package, launcher, resource layouts and RemoteViews. Room transactions can serve foreground actions, the widget and WorkManager. Alarms, notifications, document pickers, sharing and local TLS all have Android entry points. Port the JavaScript rules and verify both implementations with identical fixtures. This is the selected architecture. |
| Kotlin and SQLiteOpenHelper | Reuses the same UI and native APIs. It requires maintaining SQL mapping, invalidation and migration checks manually. Room supplies these facilities and meets the explicit storage requirement. |
| React and Capacitor | Could reuse React components and some calculation code. Existing screens call the laptop API, so offline repositories and a native SQLite bridge would still be required. The launcher widget, shared writes, reminders and background LAN sync would need Android plugins. The build would maintain Node and Android toolchains. |
| Flutter | Can package an offline app with SQLite, network and sharing plugins. Requires a new Dart UI, ported rules, a Flutter SDK on the runner and platform integration for the existing widget and background services. This checkout has no Dart implementation to reuse. |

All candidates require Android packaging tools somewhere. Build on a hosted Linux runner and keep the laptop for source editing and web regression tests. [AGP compatibility](https://developer.android.com/build/releases/agp-8-5-0-release-notes), [Room](https://developer.android.com/training/data-storage/room), [WorkManager](https://developer.android.com/topic/libraries/architecture/workmanager), [Capacitor plugins](https://capacitorjs.com/docs/plugins), [Flutter platform channels](https://docs.flutter.dev/platform-integration/platform-channels).

## Acceptance sequence

| Stage | Implementation and evidence required to exit |
| --- | --- |
| A. Baseline | Verified rollback archive with a consistent laptop DB, official wrapper checksums, hosted build of the unmodified app module, real debug artifact with manifest, size and signer. Record unit, lint and emulator outcomes separately. |
| B. Persistence | Room schema, profile and account mapping, unique habit/date keys, schedule revisions, links, immutable ledger, milestones, social cache, outbox, cursors and tombstones. Test fresh install, signed upgrade, corrupt JSON, interrupted import, duplicate import, foreign keys and concurrent UI/widget writes. Reconcile original IDs, dates, widget bindings and counts. |
| C. Offline app | Profile, theme, dashboard, habit CRUD, archive/restore, relationships, history and calendar. Compare Sunday-zero schedules, same-day revisions, fractional points and local dates across DST. Exercise writes and restart in airplane mode. |
| D. Feature parity | Match analytics, comparisons, insights, goals, XP, levels, durable awards, personal challenges and personalization with Phase 2–4 fixtures. Render real cached social results with their age. Authorize connected actions against the paired account and invalidate inaccessible content. |
| E. Android integrations and file transfer | Foreground and widget share committed state and refresh all affected widgets. Test reminder permissions, disablement, reboot and time-zone changes. Implement a common checksummed ZIP format on both platforms. Preview merge or full restore, capture recovery, apply transactionally, verify links and ledger. Test both transfer directions, repeated merge and recovery from invalid or interrupted imports. |
| F. Secure LAN sync | Pair an authenticated laptop account using single-use expiring credentials and a verified TLS identity. Store app credentials in Keystore-backed storage. Capture web and mobile writes transactionally. Persist mutation IDs, field revisions, conflicts, tombstones and per-account monotonic sequences. Commit pulled rows and cursor together. Test revoked credentials, wrong accounts, initial divergent histories, replay, offline edits to separate and identical fields, interrupted batches, opt-in Wi-Fi WorkManager jobs and manual sync. |
| G. Distribution | Pass backend, browser, Kotlin, Room and device suites. Test clean install, in-place upgrade with the original signer, reboot, widgets, reminders, laptop offline, backup and LAN round trips. Produce and inspect signed release APK, record actual logs, size, signer, supported/tested versions and installation results. |

For initial reconciliation the user reviews both inventories and collisions before associating the databases. Preserve competing field values with their mutation IDs for review. Resolve completion desired state by habit and local date and reconcile associated ledger events transactionally. Retain tombstones across offline peers. The laptop remains authoritative for social permissions. Each device owns its launcher bindings, local credentials, background scheduling and delivery state.
